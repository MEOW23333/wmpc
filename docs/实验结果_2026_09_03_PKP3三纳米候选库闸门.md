# 实验结果：PKP3 三纳米候选库闸门（2026-09-03）

## 结论

PKP3 是目前最值得保留的替代候选：公开仓库、BSD-3-Clause 许可、预测三纳米纳米片 GAAFET，模型为 PHIMO-Fusion，并提供标准单元、SRAM 和完整工艺文件。当前 ngspice-44+ 已具备加载新 OSDI 接口的能力；真正阻塞是 PKP3 原始模型尚不能由当前可用的编译器链编译为可加载产物。

## 已核验事实

- 仓库：`https://github.com/PHIMO-Group/PKP3.git`
- 固定提交：`9c38ccf3e2f5682ec7e859bcff9e41bde1e08996`
- 模型入口：`fusion_ic_nmos_lvt.va`、`fusion_ic_pmos_lvt.va`
- 模型族：PHIMO-Fusion，源自 BSIM-CMG 111.2.1，但不是 GT2N 所用的原始 BSIM-CMG 模型。
- 原始 `models/include.sp` 使用 `.hdl` 和商业仿真器风格的模型加载方式。

## 接口闸门

1. OpenVAF 23.5.0 直接编译：失败。报错包括自定义 `instance_parameter_list` 属性和常量表达式引用变量。
2. 派生语法适配后再编译：OpenVAF 在死代码优化阶段崩溃，生成越界错误；将优化级别降为 0 仍复现。
3. OpenVAF-reloaded 0.4：未能启动，预编译程序要求较新的 `GLIBC`，当前服务器为 `GLIBC 2.17`。
4. 直接把 Verilog-A 放入 ngspice：失败，当前 ngspice 报告 `.hdl` 命令未实现。

因此严格成功数为 0/3；没有进入有效工作点、直流或瞬态仿真，方程维数、内存、耗时和迭代数均不适用。

旧 OpenVAF 的崩溃已进一步定位为其内部位集越界：死代码消除阶段的位集长度为 611，却访问索引 625；`-O 0` 仍进入同一阶段。该问题发生在完成必要语法适配之后，而非 PKP3 的电路求解阶段。通过删减 PHIMO 网络变量或依赖来规避越界会改变原模型的计算图，不能作为保持物理语义的接入方案，故不再沿此路线做无约束源码删改。

对 OpenVAF-reloaded 维护分支的静态核对显示，其死代码消除仍以函数指令数分配稠密位集，并使用同一类工作队列索引机制；仅凭“新版含缺陷修复”不能证明该 PKP3 越界已经消失。自建新版编译器若获执行，应先以原始模型的最小编译作为独立闸门，失败即停止，不应把构建成功预设为模型接入成功。

## 物理正确性边界

上述结果只能证明 PKP3 在当前工具链上的接入阻塞，不能证明模型本身错误，也不能证明其与 HSPICE、商业仿真器或原始作者结果等价。若要继续，应在 `GLIBC` 足够新的服务器上直接运行新编译器；若必须在当前旧运行库服务器运行，则需在 `wmpc` 内从源码构建兼容版本的 OpenVAF-reloaded，并对原始 PHIMO 模型建立最小复现。

## 增量工具链核验（2026-09-04）

OpenVAF-reloaded 的当前说明明确指出：ngspice 44 及以上可加载 OSDI 0.3 和 0.4 模型。当前项目使用的 ngspice-44+ 因而不是该接口版本的阻塞点。维护分支提供的 64 位 Linux 二进制位于其公开下载站；从本服务器以 10 秒连接超时探测该站，未能建立连接，故尚不能判断该二进制能否在 `GLIBC 2.17` 上启动，也不能把下载不可达误记为编译或模型失败。

该编译器从源码构建至少需要 Rust 与 LLVM 18 至 21；当前服务器缺少 Rust 与可用 LLVM 工具链，但开发工具集已提供 `gcc 9.3.1`、`make 4.2.1` 和 `cmake`。官方预编译 `openvaf-r` 已实测要求 `GLIBC_2.27` 至 `GLIBC_2.39`，而本机为 `GLIBC 2.17`，不能启动。下一次有效尝试是在 `wmpc` 内准备兼容的 Rust、LLVM 和 OpenVAF-reloaded，再对未经改写的 PKP3 原始 Verilog-A 模型直接编译；只有生成 OSDI 并通过单管、反相器直流和瞬态闸门，才能继续讨论 PKP3 的物理有效性。

Python 包索引对 `openvaf` 与 `openvaf-reloaded` 的公开查询均返回不存在；环境管理器的公开通道查询在 30 秒内未返回可验证的编译器包。连同公开下载站连接超时，这些结果只说明当前服务器无法取得经来源核验的替代二进制，并不评价编译器或 PKP3 模型质量。
